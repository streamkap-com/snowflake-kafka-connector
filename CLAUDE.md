# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

This is a Streamkap fork of Snowflake's official `snowflake-kafka-connector`. The upstream `SnowflakeColumnTypeMapper` and core ingestion path (`RecordService`) are extended, not modified in place, so Snowflake upstream merges stay low-conflict — Streamkap-specific behavior lives in `Streamkap*`-prefixed classes (`StreamkapSnowflakeColumnTypeMapper`, `StreamkapSnowflakeTableSchemaResolver`, ...) that override and delegate to `super()` for anything not explicitly special-cased.

## Fork divergence from upstream — read before touching type mapping

`StreamkapSnowflakeColumnTypeMapper.mapToColumnType` is the single place that decides the destination column type for every Kafka field. It diverges from the stock `SnowflakeColumnTypeMapper` in two ways that are easy to lose track of across refactors:

1. **Debezium temporal/JSON logical types.** Upstream only recognizes plain Kafka Connect logical types (`org.apache.kafka.connect.data.{Date,Time,Timestamp}`). It has no notion of `io.debezium.time.*` or `io.debezium.data.Json` — those fall through to raw `INT`/`BIGINT`/`VARCHAR`. The Streamkap override adds explicit cases for all of them (`DATE`, `TIME(3|6)`, `TIMESTAMP`, `TIMESTAMP_TZ`, `VARIANT`). If you ever see a Debezium temporal column landing as a raw integer, this dispatch is the first place to check.
2. **Decimal → `DECIMAL(38,7)`.** Upstream returns `VARCHAR` for `BYTES` + `Decimal.LOGICAL_NAME` (lossless, string-preserving). Streamkap hardcodes `DECIMAL(38,7)` instead — a deliberate decision from STR-3827 (2025-03-17), not a Snowflake default. **This method's signature (`kafkaType`, `schemaName`) never receives the source schema's actual scale/precision** — it cannot make a scale-aware decision even if asked to. Any decimal with scale > 7 or > 31 integer digits loses precision on ingestion (ENG-2503), and the only runtime guard against this exists in `RecordService.convertToJson` (falls back to text when `precision() > MAX_SNOWFLAKE_NUMBER_PRECISION`, i.e. 38) — which catches overflow, never scale. Changing this mapping is a real product decision (round-trip fidelity vs. numeric queryability) — treat it like one: a ticket + a passing test, not a side effect of an unrelated cleanup. (This exact thing happened once already — see `b33b8b14`, "Accidental revert", 2025-05-22 — where an unrelated HexFormat cleanup collaterally reverted this to `VARCHAR` for ~6 hours before being restored.)

## Pitfalls

- **`mvn test` must pass before merging any change to `StreamkapSnowflakeColumnTypeMapper` or `RecordService`.** A stale assertion asserting `BYTES + Decimal → VARCHAR` sat in `StreamkapSnowflakeColumnTypeMapperTest` for months, failing against the actual shipped `DECIMAL(38,7)` behavior — meaning at least one merge landed without a green test run. Run the full suite, not just the file you touched.
- **Timezone-sensitive tests must pin a non-UTC, DST-observing zone.** `ZoneId.systemDefault()` vs. `ZoneOffset.UTC` bugs (see ENG-2289) are invisible on a CI runner whose default zone is already UTC — both produce identical output there. Any test of Date/Time/Timestamp conversion must wrap in `TimeZone.setDefault(TimeZone.getTimeZone("America/New_York"))` / restore-in-`finally`, and assert against two dates on opposite sides of a DST boundary (a fixed-offset bug can coincidentally pass a single-date check).
- **`TimestampConv` (the backend `AutoTimeConverters` SMT) only rewrites top-level Struct fields matching its `schema.name` filter — it never sees into `ARRAY` element schemas.** A Debezium temporal field inside an array reaches this connector with its raw `io.debezium.time.*` schema name intact, regardless of what the backend SMT chain does for scalar fields of the same logical type. `RecordService.convertToJson`'s `ARRAY` case is the only place that formats them — test it directly, not just via the scalar path.
- **A commit merged to `develop` is not evidence a fix has reached production.** Backend (`app/destinations/...`) and connector (this repo) changes for the same ticket live in different repos with independent release cadences, and backend `Prod Release` merge commits often carry a PR's intended diff to `main` well before or after the PR itself does. Verify actual deployment with `git merge-base --is-ancestor <commit> origin/main` in each repo — check the effective diff against `main`, not just whether the original PR commit is an ancestor, since later commits can supersede a PR's diff without ever containing it.
